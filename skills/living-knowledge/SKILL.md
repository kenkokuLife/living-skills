# Living Knowledge

## 用途与边界

Living 的系统视图（需求 — 实现策略 — 数据资源）是**有来源的结构化知识**的投影，不是 Agent 对代码库的一次性想象。本 Skill 规定 Agent 怎样识别、引用和渐进地补充这些知识。

- **有依据才成立。** 每个知识对象、每条关系都要能指回来源：代码位置与 Commit、文档、测试结果、用户陈述。没有来源的内容只能作为待确认的问题提出。
- **不一次性重建。** 不在每次对话或同步时重新生成整张图。只补充本次工作中真正接触并核实过的部分。
- **区分状态。**
  - 已实现 ≠ 已验证 ≠ 计划中 ≠ 候选。
  - 能力边界写明覆盖范围与未覆盖范围。
  - 候选策略不是已采用的策略。
- **用户决定。** 需求的范围、策略是否采用、能力是否算「已验证」，都由用户确认。Agent 可以提出，不能替用户批准。
- **记录不改写知识。** 工程记录（观察、验证、问题、假设……）只能通过显式关联叠加到知识对象上，不会改变需求状态或验证结论。

## 当前版本能做什么（living-skills 0.1.0 / 记录 Contract 1）

- Living 中的知识对象来自显式导入。本版本**没有**知识同步工具，Agent 不能通过 MCP 创建或修改需求、策略、数据资源。
- `project_get_context` 返回已有知识对象的 ID（`link_targets`）。工程记录用 `links` 关联到它们，关系类型见 `project_get_record_contract`。
- 新项目通常没有知识对象。这是正常的空状态，不要为了让图完整而编造对象。
- 不在 `.living/` 中自创知识文件格式。权威格式只在 Living 的 Contract 中定义。

## 怎样识别

| 知识类型 | 成立条件 | 常见来源 |
| --- | --- | --- |
| 需求 | 用户或文档明确说明要做到什么、对谁有价值 | 需求文档、Issue、用户陈述 |
| 实现策略 | 代码中真实存在的实现路径，能指出入口与关键模块 | 源码位置 + Commit、架构文档 |
| 数据资源 | 被实现实际读取或产生的数据，能说明范围与覆盖度 | 数据文件 / 表、加载代码、数据说明 |
| 能力边界 | 经测试或核查确认的覆盖范围与已知限制 | 测试结果、验证记录、用户验收 |
| 关系 | 需求由哪条策略实现、策略依赖哪些数据 | 调用链、配置、测试；不能只凭命名或时间先后推断 |

识别时写清楚三件事：看到了什么（事实与位置），推断了什么（由谁推断），还不知道什么。

## 步骤

1. 调用 `project_get_context`，看 Living 中已有哪些知识对象。
2. 本次工作涉及已有对象时，在工程记录里用 `links` 关联，并说明依据。拿不准就不关联，Living 会显示为「待关联」。
3. 发现 Living 中还没有、但有明确来源的知识，例如一个已实现的能力或一条真实的数据依赖：
   - 告诉用户，附上来源；
   - 需要留下痕迹时，写一条 `observation`（看到的事实）或 `hypothesis`（尚待验证的判断）；
   - 不伪装成知识对象。
4. 发现与已有知识矛盾的事实，例如实现与记录的策略不一致：
   - 记录为 `observation` 或 `issue`，关联到相关对象，关系用 `challenges` 或 `concerns`；
   - 不要自行修改知识的状态。

## 输出

- 给用户的知识识别说明：对象、来源、状态、未知项。
- 必要时，按 `living-records` 规范写下的工程记录。

## 兼容策略

- 后续版本加入知识同步时，本 Skill 会先升级，再由 Living 固定新的 Commit。在那之前，Agent 不应尝试提交知识对象。
- 字段与关系类型以 `project_get_record_contract` 为准；本 Skill 不复制正式 Schema。
